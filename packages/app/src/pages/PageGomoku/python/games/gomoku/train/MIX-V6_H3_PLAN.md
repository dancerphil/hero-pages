# MIX PLAN：mix-v6-h3（2026-09-23）

## 1. 目标与依据

本轮以 `nn-v6-full` 为神经网络底座，搜索与 `heuristic-v3` 的输出融合，回答：

1. **融合是否比纯 v6-full 更强？** 分别比较默认和调优后的纯 v6，区分融合收益与搜索参数收益。
2. **用什么超参数融合？** 确定 H3 value 权重 λ 与 MCTS `c_puct`。
3. **能否成为下一轮老师？** 比较 H3、现有 `mix-v5-h3`，避免仅超过底座就宣布老师升级。

这里的“融合训练”是冻结网络后的配方搜索与实战选模，不涉及梯度训练。
最终老师可交给 [V7 方案](TRAIN_V7_TODO.md) 使用；采集数据前冻结配方和搜索配置。

已核对的依据：

- manifest 中 `mix-v5-h3` 为 A3 policy + 0.5 A3 value + 0.5 H3 value，默认 `c_puct=1.2`。
- V6-base 蒸馏该老师自对弈；V6-full 又加入该老师的交叉局面标签。因此 v6 已吸收部分 H3 判断，最优 λ 未必仍是 0.5，也可能不再需要融合。
- 用户反馈后续对战中 mix-v5-h3 明显超过 v5/H3，足以支持优先探索同类融合。
- 存档 `mix-v5-h3/result.json` 的 0.5 配方 panel 得分为 69.06%，纯 A3 为 60.63%；但对 A3 仅 21–19，区间为 42.5%–62.5%，当时 `confirmed_improvement=false`。这份旧报告不能代替后续结果，也不能直接证明 v6 融合有效。
- 旧 `mix.py` 的 `BASELINE` 与 value 构造仍固定为 A3；新入口 `mix_v6_h3.py` 专用于本轮。

## 2. 方案选择

| 方案 | 做法 | 适用情况 |
|---|---|---|
| 轻量探索 | 直接试 λ=0.25/0.5，含纯 v6 对照，再调 `c_puct` | 快速判断方向，容易漏掉低权重或边界最优点 |
| **标准搜索（推荐）** | value 权重粗筛 → 两个融合权重调探索参数 → 单一冻结候选独立确认 | 同时回答是否提升与如何融合 |

以下冻结标准搜索为本轮默认计划。轻量方案若被选择，应在开始前另定候选清单与预算，不能根据阶段结果临时缩小确认标准。

## 3. 融合形式与固定条件

```text
N = nn-v6-full（v6-full/best.pth）
H = heuristic-v3
P = P_N
V = (1 - λ) V_N + λ V_H
```

- λ=0 是纯 v6；λ=1 是 v6 policy + 纯 H3 value，**不是**纯 H3。
- 首轮固定 v6-full 的 policy，仅搜索 λ 和 `c_puct`。H3 棋形权重、value 缩放、policy 温度保持当前版本。
- v6-base 可作为后续底座对照；本轮不同时搜索两个底座，避免扩大选模空间。
- 每步实际预算 5,000 ms，单 worker；统一设备、线程配置、预热、战术规则、计时边界，任务按配方/对手交错执行。
- 同一底层模型在一次融合评估内只算一次，沿用现有融合实现。
- 沿用中心黑子、邻近白子、中心 5×5 展开的四 ply 固定前缀；每个前缀换先两局，后续 `sample_moves=0`。
- screen/tune/confirm 按起始棋盘 D4 去重且相互隔离；同时排除旧 mix 搜索已使用的前缀。提前保存完整前缀及种子，确认集不用于筛选。
- 同阶段所有候选使用同一组前缀和匹配种子。限时搜索仍受机器负载影响，固定种子不保证逐手一致。
- 结论适用于上述正常开局和 5 秒预算；不从本轮推断异常开局或其他时间预算的收益。

## 4. 标准搜索流程

得分率统一为 `(胜 + 0.5 × 和) / 局数`；panel 为各对手等权平均。
开发 panel 固定为 `nn-v6-full`（默认 1.2）、`mix-v5-h3`、`heuristic-v3`、`nn-v5-a2`。
开发阶段纯 v6 对默认 v6 的同配方对局仍保留，作为同一 panel 的比较锚点，不写累计 Elo。

### A. screen：寻找有效权重区间

- λ ∈ **{0, 0.125, 0.25, 0.5, 0.75, 1.0}**，`c_puct=1.2`。
- 每对手 3 个换先开局对：6 配方 × 4 对手 × 3 对 × 2 局 = **144 局**。
- 0.125 检查蒸馏后是否只需少量 H3；0 和 1 是必要端点，0.5 复现旧老师比例。
- 按 panel 得分选出前两个 **λ>0** 的权重进入 tune；纯 v6 始终保留，不占融合名额。
- 平分先看对纯 v6 的得分，再优先较小 λ。少量对局仅用于淘汰，不输出“显著提升”。

### B. tune：联合确定 λ 与搜索探索强度

- 两个入围融合权重，各测 `c_puct ∈ {0.8, 1.2, 1.8}`。
- 纯 v6（λ=0）同样测全部三个 `c_puct`，避免只给融合模型调参。
- 每对手 5 个新开局对：9 配方 × 4 对手 × 5 对 × 2 局 = **360 局**。
- 选定 **一个融合候选 M**，以及 **一个调优纯 v6 基线 B**；保留默认纯 v6 为 B0。
- 按 panel 得分排序，平分依次看对默认纯 v6 得分、较小 λ、`c_puct` 与 1.2 的距离、较小 `c_puct`。
- 此时冻结 M/B 的完整配方。即使开发集效果不佳，也按预定预算完成确认并允许结论为“未发现收益”。
- 本轮不插入逐级细网格。若 λ 或 `c_puct` 位于边界且需要继续搜索，应另开开发实验，并为最终配方生成新的确认集。

### C. confirm：独立确认融合净收益与老师价值

固定 **50 个全新 D4 开局簇**，每个配对均换先：

| 配对 | 局数 | 回答的问题 |
|---|---:|---|
| M vs B | 100 | 同样调过搜索参数后，融合是否提升 |
| M vs mix-v5-h3 | 100 | 是否超过现有老师 |
| M vs H3 | 100 | 是否超过启发式单体 |
| M vs A2 | 100 | 不同风格对手表现 |
| B vs mix-v5-h3 / H3 / A2 | 300 | 与 M 相同外部 panel 的配对比较 |

合计 **700 局**。若 B 的 `c_puct≠1.2`，追加 M vs B0 **100 局**，作为默认配置的解释性对照；该条件在 tune 结束时确定。
确认集不再选第二个候选，不根据中途输赢改参数或提前停止。断点续跑只补预定未完成的对局。

总预算为 **1,204 局**，必要时为 **1,304 局**。这是中等以上收益的确认预算，不保证能分辨几个百分点的小提升。
旧报告平均每局约 112–143 秒，单 worker 粗估约 **38–52 小时**；实际用本轮 screen 的耗时更新预计完成时间，保持预定局数。

## 5. 统计口径与晋级标准

### 记录与区间

- 报告整体、逐对手及黑白 W-D-L/得分率；记录 quiet 平均访问数、实际落子耗时和整局耗时。
- 以开局为簇 bootstrap，至少 10,000 次重采样，固定统计种子。一个簇包含该开局全部颜色、候选与对手，不能把两局换先当独立样本。
- 外部 panel 固定为 **旧 mix / H3 / A2**。计算每个开局下 `M panel score - B panel score`，对差值做配对区间；不能靠两个独立区间是否重叠判断差异。
- 常规报告给出 95% 区间；正式判断对下面四个指标使用 Bonferroni 校正的 **98.75% 双侧区间**，控制本轮四项比较的总体错误率不高于约 5%（bootstrap 近似）。

### 四个预先指定指标

1. M vs B 得分率相对 50% 的差值。
2. M vs 旧 mix 得分率相对 50% 的差值。
3. M vs H3 得分率相对 50% 的差值。
4. M 与 B 的外部 panel 得分率差值 Δ。

判定分层：

- **支持融合提升**：指标 1 的校正区间下界 >0，且直接交手得分率 ≥55%；同时 Δ 点估计 ≥0，其校正区间下界 >−3 个百分点（预定非劣界）。
- **支持老师升级**：满足融合提升，且指标 2、3 的校正区间下界均 >0。
- **支持综合对手提升**：仅当指标 4 的校正区间下界 >0 时额外声明。
- 黑白分项与 A2 单独交手作为诊断，明确报告明显退化；不事后新增显著性门槛或挑选有利对手。

未过门槛区分“结果倾向无益”和“区间仍宽、证据不足”，不能直接断言融合无效。
默认保留现有老师；若仅支持相对 v6 提升，可以保留候选，但不能宣称超过旧老师。
如需扩充证据，另立固定预算的独立复核；不在同一确认集上反复追加直到显著。

## 6. 输出与冻结配方

复用现有逐局落盘、指纹与续跑机制，目标目录为 `python/games/gomoku/checkpoints/mix-v6-h3/`：

- `config.json`：候选网格、晋级规则、设备/预算、前缀、种子、manifest 与依赖源码/权重哈希。
- `games.jsonl`：逐局任务、配方、开局、搜索统计、结果及耗时。
- `screen.json` / `tune.json`：所有配方的成绩，不能只保留赢家。
- `selection.json`：确认前冻结的 M/B/B0、排序依据与确认配对表。
- `confirm.json`：直接交手、共同 panel、配对差值区间、黑白分项与吞吐。
- `result.json`：`fusion_improved`、`teacher_upgrade_supported`、最终建议及证据不足原因。
- `teacher-manifest.json`：仅在支持老师升级时输出待合并的 `mix-v6-h3` 条目；其他情况在结果中保留候选配方。

候选 manifest 形状如下（λ 和 c 均由 tune 选定，不能预先把 0.5/1.2 当成最终答案）：

```text
mix-v6-h3:
  policy: nn-v6-full
  value: {nn-v6-full: 1-λ, heuristic-v3: λ}
  c_puct: c
```

评测目录独立保存，不写训练库或累计 Elo。正式登记后，下一轮数据批次记录冻结老师版本；已有 V6 训练记录仍引用原来的老师。

## 7. 执行与续跑

项目根目录运行（全局默认 `python`）：

```sh
pnpm mix
```

入口是 `python/games/gomoku/train/mix_v6_h3.py`，默认执行以上标准流程。
目录迁移改变了源码指纹；旧 tune/confirm 保留作历史记录，新实验默认写入 `python/games/gomoku/checkpoints/mix-v6-h3-after-layout/`。
中断后同一命令续跑，仅补未完成对局。输出目录有进程锁；配置、代码、权重或运行环境改变时必须使用新目录。
逐局结果 flush/fsync，报告原子替换；写入被中断的末行会丢弃并重跑该局，完整记录损坏直接报错。

默认排除 `python/games/gomoku/checkpoints/mix-v5-h3/config.json` 中所有阶段的开局。
如果还有其他旧搜索，开始前通过可重复的 `--exclude-config` 加入，文件必须存在。
确认报告的 `results` 是各候选全部已排定对手的汇总（M/B 对手数不同），共同对手比较应读 `external_panel` 和 `metrics.panel_delta`。

可在运行前选择轻量探索，仍保留独立确认：

```sh
pnpm mix --weights 0.25 0.5 --output python/games/gomoku/checkpoints/mix-v6-h3-light
```

λ=0 自动加入；`--weights` 至少包含两个不同的正权重。可调整 `--c-puct`、`--screen-pairs`、`--tune-pairs`、`--confirm-pairs`、`--seed`、`--time-ms` 和 `--workers`。
所有 pair 参数均为每个配对的换先开局数。默认每个 worker 的 PyTorch intra/inter-op 线程均为 1，设备自动选择 CUDA/MPS/CPU。
增加 worker 会改变设备竞争，不将并发的访问数下降误判成模型本身变差。

## 8. 与 V7 的交接边界

**融合老师的加载、搜索和采集接口无需新增改造。** 导出的配方符合现有 manifest 契约，`c_puct` 会由模型属性自动传到 MCTS；保存的 π/q、战术标记及黑白模型名沿用现有格式。

通过老师升级门槛后：

1. 将 `teacher-manifest.json` 中的 `mix-v6-h3` 条目合并进 `python/games/gomoku/checkpoints/manifest.json`。这只是一个条目片段，不是覆盖整个 manifest 的文件。
2. 在 `python/games/gomoku/selfplay/config.py` 中将 `CONFIGS["teacher"]["models"]` 改为 `["mix-v6-h3"]`，检查采集局数和预算，再执行 `pnpm teacher`。该模式即采集新老师自对弈。
3. 如需交叉对局，将 `CONFIGS["update-elo"]["models"]` 改为 `["mix-v6-h3"]` 后执行 `pnpm update-elo`；现有模式会对全部已注册其他模型安排交手。
4. 记录实际生成的 batch ID，将搜索目录的 `config.json`、`selection.json`、`result.json` 与老师条目一同作为该批次的来源依据。保持底层 checkpoint、H3 代码和配方不变；版本改变时使用新模型名和新批次。
5. V7 训练读取这些新采集批次；本次调参/确认的固定前缀对局只用于评测，不自动导入训练库。

当前 `selfplay_batches` 只保存配对、预算和采样配置，不内置权重/源码哈希；上述冻结信息需随批次保存，不能仅凭模型名认定版本一致。

**完整 V7 训练仍有独立待办。** [TRAIN_V7_TODO.md](TRAIN_V7_TODO.md) 的 90/10 或 85/10/5 多来源方案，需要实现逐步标签来源识别、获胜对手筛选、分来源抽样与切分；现有 V6 loader 不支持直接套用该方案。
本轮老师不引入额外接口要求，也不要求全量重分析。老师选定后，V7 再按其既定计划实现训练数据管线。

旧入口说明归档在 [MIX_V5_H3.md](MIX_V5_H3.md)；历史实验结果仍保留原位置。
